# 定时充放电（TOU）开放方案

> 实施修订：已在盛弘 profile 中实现，按协议寄存器写入，尚未经过实机验证。没有总开关时，先把工作模式切到自发自用，再逐块写入并回读，完全一致后才恢复或激活，失败不自动激活。生效日期写为“当天 ~ 2099-12-31”；暂不支持跨零点；24:00 一律拒绝，不改写为 23:59。这些假设见 [FIRMWARE_QUESTIONS.md](FIRMWARE_QUESTIONS.md)（Q5、Q10）。下文是原始方案讨论，冲突处以代码为准。

> 对应工作模式 `0x300C = 1 定时充放电`。原则：用户可见的参数能少尽量少。
> 点位依据 V001B031 第 9 章和附录三。竞品情况来自公开的社区项目，见文末参考。

## 1. 结论

**界面上只加 1 个实体，配置走集成的“选项”页面，自动化走 1 个整表替换服务。**

| 用途 | 形式 | 给谁用 |
|---|---|---|
| 查看 | `sensor.tou_schedule`（定时充放电计划）：状态是“当前生效的时段”，属性是完整时段表 | 所有用户 |
| 手动编辑 | 集成 → 配置 → **“定时充放电”选项页面**（HA 原生表单，含时间、数字、星期选择器） | 普通用户 |
| 自动化 / 动态电价 | 服务 `energylib.set_tou_schedule`（整表替换）和 `energylib.clear_tou_schedule` | 进阶用户、EMHASS / Predbat 一类工具 |

**不采用**每个时段拆成一组实体的做法（Solis、Deye 社区集成是这样做的）。原因见第 3 节。

## 2. 盛弘协议里的时段参数

| 地址 | 内容 | 编码 |
|---|---|---|
| 0xC014~0xC042 | 6 组 ×（充电开始、充电结束、放电开始、放电结束），共 24 个 float | 时间按 HHMM 存成 float，例如 `10:00` 存为 1000，范围 [0,2359] |
| 0xC0BA~0xC0D0 | 6 组 ×（充电功率、放电功率），共 12 个 float | kW，[0,50] |
| 0xC0B4 | 重复周数 | U32 位图，bit0 = 周日 … bit6 = 周六 |
| 0xC0B6 / 0xC0B8 | 生效起始 / 结束日期 | U32 时间戳，**把本地时间当作 UTC 换算**，只取年月日，**默认值是今天** |
| 0x314E | 时段外模式 | 0 自发自用、1 备电、2 光伏优先充电、3 光伏优先卖电 |
| 0x300C | 工作模式 | 1 = 定时充放电，设成 1 后时段才生效 |

附录三的规则：
- 同一组里充电和放电重叠时，充电优先；
- 不同组之间重叠时，序号小的优先；
- 开始时间等于结束时间的时段不生效。

原始参数共 **40 个**（24 + 12 + 1 + 2 + 1）。如果每个都做成实体，设备页会多出 40 个控件。

## 3. 竞品做法对比

| 做法 | 代表 | 优点 | 问题 |
|---|---|---|---|
| A. 每个时段拆成多个实体（time + number + switch） | Solis Modbus、Deye 社区集成：每个时段有开始、结束时间实体，充电使能开关，SOC/功率 number | 可以在仪表盘上直接改 | 实体数量多，套到盛弘协议上就是 40 个；**每改一个字段就写一次设备，中途会出现“开始时间晚于结束时间”“与其他时段重叠”这样的半成品计划，设备会按半成品执行**；重叠规则没法逐个实体校验 |
| B. 服务 + 1 个只读传感器 | 华为 `huawei_solar.set_tou_periods`：每行一个时段 `05:00-06:00/1234567/+`，整表替换；用传感器显示当前计划 | 实体少，整表原子写入，适合自动化 | 普通用户要在“开发者工具”里写字符串，门槛高；华为社区反映结束时间写 00:00 会报错 |
| C. 服务修改单个时段 + 服务修改全部时段 | Fox ESS（`update_charge_period` / `update_all_charge_periods`） | 自动化灵活 | 仍然没有普通用户的界面 |
| D. 外部 EMS 实时调度 | 思格 Remote EMS，搭配 Predbat / EMHASS | 最灵活 | 需要 HA 常驻在线，不是“设置一次就不用管”的 TOU |

**本方案 = B + 原生选项页面**：用华为的整表原子写入，补上普通用户能直接操作的原生界面；实时调度交给我们已规划的 P4 远程充放电（`0xC646/0xC648`）。

## 4. 面向用户的数据模型（隐藏协议细节）

用户看到的是一张**时段列表**，不是“6 组充电 + 6 组放电”的寄存器：

| 字段 | 用户看到的 | 默认值 |
|---|---|---|
| 类型 | 充电 / 放电 | — |
| 开始 / 结束 | 时间选择器，精确到分钟 | — |
| 功率 | kW 滑块，上限取机型额定功率 | 额定功率 |
| 生效星期 | 星期多选，所有时段共用一个设置 | 每天 |
| 时段外模式 | 下拉：自发自用 / 备电 / 光伏优先充电 / 光伏优先卖电 | 自发自用 |

**不给用户看**：
- **生效日期**：集成固定写成“今天 ~ 一个很远的日期”。协议默认结束日期就是今天，不处理的话计划**第二天就失效**。可写入的最大日期需要确认 ⚠。
- **时段序号**：保存时按开始时间排序，再依次分配到第 1~6 组。
- **未使用的组**：开始、结束都写 0，按规则 2.3 视为不生效。

## 5. 选项页面流程

```
集成卡片 → 配置
  └─ 菜单：定时充放电
       ├─ 当前计划（只读预览，按时间排序）
       ├─ 添加时段：类型 / 开始 / 结束 / 功率 → 实时校验
       ├─ 编辑或删除时段：从列表中选择
       ├─ 生效星期 / 时段外模式
       ├─ 从模板创建（v2）：谷电充电 / 峰时放电 / 谷充峰放，按用户填写的峰谷时段生成
       └─ 保存
            ├─ ☐ 保存后切换为“定时充放电”模式（工作模式不是 1 时显示）
            └─ 一次写入整张表 → 回读比对 → 成功或失败提示
```

所有修改先在页面里暂存，**点“保存”时才一次写入设备**。这样设备不会收到半成品计划。

## 6. 校验规则（页面和服务共用）

| 规则 | 处理 |
|---|---|
| 充电、放电各最多 6 段 | 超出时报错，并提示合并时段 |
| 开始时间 = 结束时间 | 拒绝 |
| 任意两个时段重叠（包括充电和放电之间） | **直接拒绝**，不依赖设备的“充电优先 / 序号优先”规则，避免用户看到的和实际执行的不一致 |
| 跨零点，例如 22:00~06:00 | 设备是否支持开始时间大于结束时间待确认 ⚠；不支持时自动拆成 22:00~23:59 和 00:00~06:00，占用 2 段，并提示用户 |
| 结束时间 24:00 | 协议最大值是 2359，存为 23:59，界面上说明 |
| 功率 | 0 ~ min(50, 机型额定功率) kW |
| 时段外模式 = 备电 | 提示：时段外电池不放电 |

## 7. 服务定义

```yaml
energylib.set_tou_schedule:
  device_id: <逆变器>
  periods:                      # 整表替换；空列表表示清空
    - {type: charge,    start: "01:00", end: "06:00", power: 5}
    - {type: discharge, start: "18:00", end: "22:00", power: 3}
  weekdays: [mon, tue, wed, thu, fri, sat, sun]   # 可选，默认每天
  outside_mode: self_consumption                  # 可选，默认不改
  activate: true                                  # 可选，是否同时把 0x300C 设为 1

energylib.clear_tou_schedule:
  device_id: <逆变器>
```

**服务也接受华为风格的简写字符串**（`01:00-06:00/1234567/+5`），方便从华为迁移过来的用户和现有模板复用（v2）。

## 8. 写入过程

1. 确认集成选项里已打开“允许控制”，并检查与 P4 远程控制的互斥：远程控制打开时禁止修改计划，或先提示用户关闭远程控制。
2. 按第 6 节校验，然后排序、分组。
3. 用 3 帧 FC16 写入：
   - 0xC014~0xC043：24 个 float，48 个寄存器
   - 0xC0B4~0xC0B9：星期 + 生效日期，6 个寄存器
   - 0xC0BA~0xC0D1：24 个寄存器
4. 需要时再写 0x314E 和 0x300C。
5. 回读以上全部地址并逐项比对；不一致时报错，并在传感器上标出“设备计划与 HA 不一致”。
6. 每 5 分钟重读一次计划：用户可能在 App 或屏幕上改过，以设备为准，不覆盖设备上的修改。

## 10. 需确认 ⚠

1. 定时充放电有没有总开关？附录三写的是 `0xC0B0`，但正文里这个地址是“12V 供电开关”。还是只要 0x300C = 1 就生效？
2. 时段是否支持跨零点（开始 > 结束）？
3. 生效结束日期可写入的最大值是多少？是否支持“永久有效”？
4. 写完时段后是否需要重新写 0x300C，或者等待生效？
5. 充电功率是从电网取电，还是光伏优先、电网补足？放电功率是否受防逆流（0x3002/0x3004）限制？
6. 计划电价模式（0xC2A0、今日 / 明日计划 0xC31A~0xC378）和定时充放电是什么关系？是否更适合对接动态电价？

## 11. 多厂家通用：标准 TOU 模型

选项页面、服务和计划传感器只依赖标准模型，不依赖盛弘的寄存器；各厂家的差异用 `TouLimits` 声明，界面按声明自动显示或隐藏字段。

```text
TouSchedule
  periods: [TouPeriod(type=charge|discharge, start, end, power_kw?, target_soc?, weekdays?)]
  weekdays: 整张表共用的生效星期（用于不支持逐段设置星期的设备）
  outside_mode: 标准工作模式枚举

TouLimits（由 profile 声明）
  max_charge_periods / max_discharge_periods   # 盛弘 6/6；Fox ESS 2 个充电时段
  shared_slots: bool                           # 充电和放电是否共用一组时段（Deye 的 6 个 Program）
  supports_power / supports_target_soc         # 盛弘有功率、没有目标 SOC；Deye 有 SOC
  weekdays: none | shared | per_period         # 盛弘 shared；华为 per_period
  supports_cross_midnight: bool                # 盛弘待确认 ⚠
  time_resolution_min: 1                       # 有的设备只能按 15 / 30 分钟设置
  overlap_policy: reject                       # 统一拒绝重叠
```

| 厂家 | 时段数量 | 功率 | 目标 SOC | 星期 | 对应的 TouLimits 要点 |
|---|---|---|---|---|---|
| 盛弘 V001B031 | 充 6 + 放 6 | ✔ | ✘ | 整表共用 | `max_*=6, weekdays=shared` |
| 华为 | 不限（按行） | ✘ | ✘ | 逐段 | `weekdays=per_period, supports_power=False` |
| Deye / Sunsynk | 6 个共用 Program | ✔ | ✔ | 整表共用 | `shared_slots=True, supports_target_soc=True` |
| Fox ESS | 2 个充电时段 | ✘ | ✘ | ✘ | `max_charge_periods=2, max_discharge_periods=0` |

> 表中盛弘以外的数据来自社区项目，仅用于验证这个模型能覆盖它们，实际接入时以厂家协议为准。
